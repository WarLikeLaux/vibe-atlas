# Запуск исследовательских агентов в HAPI

HAPI запускает отдельные сессии агентов. Каждая сессия получает исследовательское задание по [общему регламенту](research-workflow.md). HAPI развивается в отдельном репозитории, его локальные настройки и идентификаторы сессий хранятся вне Vibe Atlas.

Порядок проверен 11 октября 2026 по справке `hapi --help`, документации HAPI для агентов, исходникам команд и доступным инструментам MCP. Состав инструментов нужно проверять заново после обновления HAPI. Исследовательские карточки, которые можно опубликовать, передаются в этот репозиторий.

## Подготовить задание

1. Заполнить [шаблон задания](templates/research-task.md): роль, область поиска, период, граница партии и ожидаемый результат.
2. Выделить отдельную папку `research/proposals/<task-id>/`. У параллельных исполнителей должны различаться идентификаторы заданий и области поиска.
3. Указать обязательные документы проекта и подходящий шаблон карточки. Результат и условия важнее полноты телеметрии, недостающие токены отдельно не ищутся без поручения на анализ расходов.
4. Ограничить изменения поискового агента своей папкой. Общие каталоги, импорты и интерфейс меняет исполнитель интеграции после проверки. Разработка кода требует отдельного задания и соблюдения правил проекта.

Первое сообщение содержит готовое поручение или относительный путь к сохранённому файлу задания. Если передаётся путь, агент должен иметь доступ к той же рабочей копии и прочитать файл перед началом работы. Не передавать персональные настройки вместе с публичной карточкой.

## Создать сессию сейчас

В интерфейсе HAPI нажать плюс, выбрать проект и агента, создать сессию и отправить подготовленное задание. Проверить рабочую папку и выбранную конфигурацию перед отправкой.

Для запуска из интерактивного терминала выполнить одну команду из корня рабочей копии проекта:

```sh
hapi codex
```

Вместо `codex` указать нужный поддерживаемый драйвер агента. Запускать только выбранного исполнителя, затем отправить ему задание один раз. Флаги модели, effort и прав зависят от драйвера. Не переносить параметры одного агента на другой и не угадывать идентификатор модели.

Общая справка доступна через `hapi --help`. Не проверять справку запуском `hapi <agent> --help`: некоторые обёртки создают сессию даже с таким аргументом. Создание сессии через runner из фонового процесса отличается от интерактивного запуска. Для автоматического запуска использовать MCP-инструмент `launch_agent`, описанный ниже.

## Найти исполнителя и передать поручение через MCP

На дату проверки доступны инструменты работы с существующими сессиями:

| Инструмент     | Действие                                                               |
| -------------- | ---------------------------------------------------------------------- |
| `list_peers`   | Найти сессии на том же хабе                                            |
| `inspect_peer` | Прочитать метаданные и последние сообщения без возобновления работы    |
| `ping_peer`    | Отправить сообщение выбранной сессии, при необходимости возобновить её |

1. Найти сессию через `list_peers` и проверить через `inspect_peer`, что это нужный агент и проект. Использовать полный идентификатор, когда он известен.
2. Если пользователь поручил передать работу этому агенту, вызвать `ping_peer` с его идентификатором и готовым заданием. Если задание уже отправлено в интерфейсе, повторно его не отправлять.
3. Зафиксировать связь задания и сессии в приватной рабочей заметке. В публичную папку передачи включать только результаты исследования.
4. Проверять ход работы через `inspect_peer`. Флаг активности не подтверждает выполнение задания, готовность определяется сообщениями исполнителя и фактическими файлами.
5. Перед интеграцией сверить карточки, соответствия моделей и дубликаты по регламенту. После изменения общих данных выполнить `npm run check`.

`ping_peer` работает с существующей сессией и принимает необязательный `requestId` сообщения для защиты повторной доставки. При ошибке или таймауте отправки сначала проверить сообщения через `inspect_peer`, чтобы выяснить, доставлено ли поручение. Для повтора использовать тот же идентификатор сообщения.

## Автоматический запуск через MCP

11 октября 2026 инструменты доступны в текущем HAPI MCP. Через них создана первая партия из шести Codex-сессий, для каждой получено `messageDelivered: true`, затем через `inspect_peer` подтверждено начало работы. Проверка повторного запроса в этой партии не проводилась, условия повторов ниже взяты из контракта инструмента.

1. Вызвать `list_launch_options` и выбрать доступный проект и агент. Ответ содержит локальную инвентаризацию, его нельзя сохранять в публичных файлах.
2. Вызвать `launch_agent` с `project`, `agent`, `message` и уникальным `requestId` задания. Проект задаётся возвращённым путём или уникальным именем. Модель и effort можно опустить, будут использованы родные настройки агента. По контракту права по умолчанию максимальные, режим удалённый. Полномочия задачи по-прежнему определяет поручение пользователя.
3. Сохранить ответ приватно. Успешный ответ содержит `sessionId`, ссылку `url` и `messageDelivered`.
4. Проверить начало работы через `inspect_peer`. Не отправлять то же первое задание через `ping_peer`, если доставка уже подтверждена.

Пример вызова после проверки доступности проекта:

```json
{
    "project": "vibe-atlas",
    "agent": "codex",
    "message": "Прочитай research/proposals/<task-id>/task.md и выполни задание. Пиши только в своей папке.",
    "requestId": "<unique-task-request-id>"
}
```

Для повтора использовать тот же `requestId` и идентичные параметры. Защита повторного запуска действует в пределах времени жизни MCP-сервера вызывающей сессии. После его перезапуска сначала проверить существующие сессии. Если результат создания неизвестен, автоматический повтор запрещён контрактом инструмента: сначала найти сессию через `list_peers` и сверить её сообщения. Новый самостоятельный запуск получает новый идентификатор запроса.

Доступны необязательные `model`, `effort`, `permissionMode`, `machineId` и `worktreeName`. Дополнительный worktree создаётся при необходимости разработки кода. Для исследовательских карточек в общей рабочей копии достаточно отдельных папок передачи. Текущие незакоммиченные документы нужно учитывать при выборе другой рабочей копии.
